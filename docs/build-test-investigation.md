# build & testの高速化調査

調査日: 2026-10-04。実装更新: 2026-10-05。調査対象のコミットは`97bd27b44108f2448abf65a226ed47775d30bf4b`。対象はVS Codeの`build & test`による解答のコンパイルとサンプルテスト。開発コンテナの初回構築とは別の処理である。

## 結論

最初に比較する候補は、既存の`lld`を使う`-fuse-ld=lld`である。コンテナに追加パッケージを入れず、`-O2`と全ライブラリ指定を維持して試せる。次に、ヘッダーの読み込み範囲を減らすか、プリコンパイル済みヘッダー（PCH）で解析を再利用する。

ただし、利用者の環境で何秒短縮できるかは未測定。この調査環境はARMで、配布コンテナはx86-64専用のため、配布環境の速度や156個のライブラリを指定したリンク時間をここでは測れない。補助測定と、実際のコンテナで実行する測定手順を分けて記録する。

## 適用した変更（2026-10-05）

利用者が提案方針を承認したため、通常ビルドとデバッグのタスクに`-fuse-ld=lld`を追加した。`-O2`と全ライブラリ対応を維持し、ソース・ヘッダー・マクロ・コンパイラの設定はそのまま使う。タスクはワークスペースから読まれ、現在の配布イメージにLLDが入っているため、イメージの発行やコンテナ再構築をせず反映できる。

構成テストは、LLD指定、空白・シェル展開文字を含む解答パス、サンプルテストの引数、コンパイル失敗時のテスト停止を確認するよう更新した。コンテナ検証にも、LLDの実使用、12ライブラリ、OR-Toolsの全ソルバー、サンプル、GDBの確認を追加した。起動時の既定リンカーによるライブラリ確認も残している。

PCHの自動適用は今回は見送った。現在の`-fmodules`と併用できず、無効化すると`__cpp_modules`による条件分岐も変わるため、正式設定との互換性を保ったまま加えられる変更ではない。今後、対象の解答で両設定の動作が一致することを検証したうえで、利用条件を限定する案を検討する。

構成検証と実際のaccを使う雛形・移行検証は成功した。ARM・GCC 13.3の補助環境にもUbuntuのLLD 18.1.3を一時領域へ展開し、変更後のタスクを実行した。3サンプルの成功、LLDが実際に使われたこと、GDBでの停止・正常終了、空白やシェル展開文字を含む解答パスの扱い、コンパイル失敗時のテスト停止を確認した。

同じ合成解答で、1回ウォームアップ後に3回測定した中央値は次のとおり。[LLD比較結果](benchmarks/build-test-lld-gcc13-arm.json)を保存した。

| 測定 | BFD | LLD |
| --- | ---: | ---: |
| リンク単体 | 0.058秒 | 0.030秒 |
| ビルド＋3サンプルテスト | 5.311秒 | 5.289秒 |

追加ライブラリのない補助環境ではリンクは約49%短縮したが、全体の差は約0.4%で、ビルドのばらつきと比べても小さい。これを大幅なビルド高速化の証拠とは扱わない。通常ビルドのヘッダー解析時間は残っている。

配布環境のGCC 15.2・156個の追加リンク指定での実行速度と、12ライブラリ・OR-Tools・LibTorchのLLD互換性は、このARMホストでは未検証である。追加したコンテナ検証は、その環境で実行するためのもの。採用効果の確定には配布環境の測定結果が必要となる。

## 調査開始時の処理と根拠

| 段階 | 実装から確認できること | 高速化で確認する点 |
| --- | --- | --- |
| タスク起動 | [tasks.json](../.vscode/tasks.json)は`atcoder-g++ "$1" -o a.out && oj test -c ./a.out -t 2`を毎回実行 | 再テストだけでも再コンパイルする |
| ヘッダー解析 | [C++雛形](../config/atcoder-cli/cpp/main.cpp)は`atcoder/all`、`bits/stdc++.h`の順に読み込む | 必要なヘッダーだけにする場合との比較、PCHの利用条件 |
| コンパイル | [ラッパー](../.devcontainer/scripts/atcoder-g++)が公式レシピ由来の設定を渡す。通常は`-O2`、デバッグは後置の`-g -O0`で上書き | 最適化時間とヘッダー解析時間を分ける |
| リンク | [prepare.py](../.devcontainer/atcoder/prepare.py)が189個のフラグから156個の`-l`指定を抽出し、ソース・オブジェクトの後ろへ渡す | オブジェクトからのリンク単体で、既定リンカーと`lld`を比較 |
| テスト起動・実行 | ビルド成功後に`oj test`を起動。`-t 2`はサンプルごとの実行時間制限 | Pythonツールの起動時間と実際の解答実行時間を区別 |

156はリンクフラグの数であり、実行ファイルに156個のライブラリ全体を取り込むという意味ではない。ライブラリの探索やシンボル確認の費用が候補となる。実際にどのファイルが選ばれるかはリンク時のトレースで確認する。

[保存済み公式レシピ](../.devcontainer/atcoder/gcc.toml)ではBoost、LightGBM、OR-Toolsなどを静的ライブラリとして構築し、LibTorchは共有ライブラリの配布物を使う。`--as-needed`は共有ライブラリへの実行時依存を制御する設定であり、静的ライブラリの探索をなくす設定ではない。[GNU ld公式文書](https://sourceware.org/binutils/docs/ld/Options.html)

現在のレシピには`-flto`がなく、生成処理と構成検証でも不使用を確認している。LTOを外す案は現状への追加改善にならない。上流レシピを再取得したSHA-256も保存版と一致した（`76c63a226f4fa45511bd62823e7a9ff7bc5a481d04e07371b0d09a7beb752855`）。AtCoderも2026年6月に`-flto=auto`の削除を告知している。[AtCoder公式告知](https://atcoder.jp/posts/language_update20260616_jp)

## 補助測定

Ubuntu 24.04、ARM（aarch64 / Neoverse N1）、GCC 13.3.0、ACL 1.6で測定した。CPU affinityを2 CPUに制限し、プロセスの仮想アドレス空間上限を4 GiBに設定した。これはDockerの`--cpus=2 --memory=4g`と同じ資源制限ではない。

各ケースは1回ウォームアップ後に3回実行し、その実時間の中央値を使った。利用者の解答ではなく、Fenwick treeで点加算・区間和を行う短い合成解答である。標準の雛形そのものも別に測定した。全ヘッダー版と必要ヘッダー版は解答処理が同じ。

| 測定 | 中央値 |
| --- | ---: |
| 標準のC++雛形、`-O2` | 4.787秒 |
| 合成解答、全ヘッダー、`-O2` | 4.846秒 |
| 同じ解答、`iostream`と`atcoder/fenwicktree`のみ、`-O2` | 0.582秒 |
| 合成解答、全ヘッダー、`-O0` | 3.721秒 |
| 合成解答、全ヘッダー、`-O1` | 4.201秒 |
| コンパイル単体、全ヘッダー、`-O2` | 4.773秒 |
| コンパイル単体、必要ヘッダーのみ、`-O2` | 0.533秒 |
| リンク単体、通常の標準ライブラリ構成、BFD | 0.057秒 |
| 共通ヘッダーのPCH生成 | 7.037秒 |
| 同じ解答、PCH利用、`-O2` | 2.416秒 |
| コンパイル単体、PCH利用、`-O2` | 2.358秒 |
| `oj test --help`起動 | 0.428秒 |
| `oj test`で3サンプルを確認 | 0.474秒 |
| ビルド＋3サンプルテスト、全ヘッダー | 5.363秒 |
| ビルド＋3サンプルテスト、必要ヘッダーのみ | 1.052秒 |
| ビルド＋3サンプルテスト、PCH利用 | 2.884秒 |

この小さな解答ではヘッダーを絞ると約88%短縮した。最適化を`-O0`へ下げる短縮は約23%、`-O1`は約13%で、ヘッダーを絞る効果より小さい。

PCHなら全ヘッダーを維持して約50%短縮した。生成費用7.037秒を、1回あたり約2.43秒の短縮で回収するには約3回のビルドが必要となる。生成物は179,605,488 bytes（約171 MiB）だった。`-H`の出力で`.gch`に`!`が付くことを確認しており、通常解析へのフォールバックではない。`!`は有効なPCHを表す。[GCCのヘッダートレース仕様](https://gcc.gnu.org/onlinedocs/gcc/Preprocessor-Options.html)

サンプルテスト込みでは、必要ヘッダーだけの構成で約80%、PCHで約46%短縮した。18ケースすべてでウォームアップと3回の測定が成功し、全ヘッダー・必要ヘッダー・PCHそれぞれの解答が同じ3サンプルを通った。[実測の全ログと入力](benchmarks/build-test-gcc13-arm.json)を保存した。

この環境の全ビルドには正本の156個の追加リンク指定がなく、GCC 15.2用の`-fmodules`も渡していない。したがって、上の秒数・割合を利用者の環境へそのまま当てはめることはできない。ここで測ったリンク単体の0.057秒も、配布環境でのリンク時間を表さない。`lld`はホストに存在せず、その短縮効果は未測定である。

## 利用中のコンテナでの再測定

[測定スクリプト](benchmarks/build-test.py)はPython標準ライブラリだけを使う。既存の解答や`a.out`には触れず、一時ディレクトリで合成解答をコンパイルする。PCHも一時領域に生成して削除する。コンテナ内で、リポジトリのルートから次を実行する。

```bash
python3 docs/benchmarks/build-test.py --output /tmp/atcoder-build-results.json
```

配布環境では`flags.sh`と`atcoder-g++`を使用して、全リンク指定でのビルド、コンパイル単体、リンク単体、`lld`、必要ヘッダー、最適化設定、PCH、`oj`単体、ビルド＋テスト全体を比較する。PCHのケースだけは後述の理由で`-fno-modules`を追加し、PCHなしで同じフラグにした対照ケースも測る。JSONに各コマンド、環境、各回の時間、失敗・スキップを残す。

2 CPU・4GBで独立したDockerコンテナを使う場合は次のように実行できる。結果はホストの`.build/benchmarks`に残る。最初に固定イメージの取得が必要な場合、その時間は解答ビルドの測定には含まれない。

```bash
mkdir -p .build/benchmarks
docker run --rm --cpus=2 --memory=4g \
  --user "$(id -u):$(id -g)" --entrypoint python3 \
  --volume "$PWD:/workspace:ro" \
  --volume "$PWD/.build/benchmarks:/results" \
  ghcr.io/foxy-null/atcoder-devcontainer-template@sha256:9d514740847fb5e4ffb23ce04d9771636539f3997559948ceb7165a1d9bb5f7e \
  /workspace/docs/benchmarks/build-test.py --output /results/build-test.json
```

このDockerコマンドはx86-64ホスト向け。実際の待ち時間を確認するときは、利用中のコンテナの資源量・保存場所でも測定する。合成解答は処理の切り分けに使い、採用前には利用者の代表的な解答でも効果を確認する。

JSONで`median_wall_s`が`null`なら、そのケースは成功した速度比較として扱わない。PCHは`PCH_used: true`の確認が必要。既定環境で使えることを確認できた範囲は、今回のARM補助測定であり、配布コンテナでのスクリプト実行・リンカー互換性は未確認である。

## 改善候補

### 1. 既存のlldでリンクする

[Dockerfile](../.devcontainer/Dockerfile)には既に`lld`のインストールが含まれる。試験用のビルドに`-fuse-ld=lld`を追加すればよい。GCC 15.2がこの選択をサポートする。[GCCのリンクオプション](https://gcc.gnu.org/onlinedocs/gcc-15.2.0/gcc/Link-Options.html)

採用前に、リンク単体とビルド全体の中央値を比較する。リンクが支配的なら有力、ヘッダー解析が支配的なら全体への効果は小さい。既存の12ライブラリ確認コード、OR-Toolsのソルバー、LibTorch、サンプルテスト、GDBも候補設定で確認する。

リンカーを変えると、静的ライブラリの探索規則も変わる。`lld`で成功したコードが既定リンカーで失敗する場合もあるため、提出互換性の確認では既定リンカーでの成功も維持する。`--warn-backrefs`は差を調べる補助となる。[LLDの公式説明](https://lld.llvm.org/ELF/warn_backrefs.html)

### 2. 必要なヘッダーだけを読む

`bits/stdc++.h`は標準ライブラリを広く読み込み、`atcoder/all`はACL全体を読み込む。問題に必要な標準ヘッダーとACLの個別ヘッダーに絞る案を、同じ解答処理で比較する。

この案は編集後の毎回のビルドに効き、新しい依存やキャッシュ管理が不要。ただし、何でもすぐ使える雛形の利便性を下げる。雛形を変えても既に作成された解答には反映されないため、既存解答への対応と次回取得分への対応を分ける。

### 3. 共通ヘッダーをPCHにする

共通ヘッダーの解析結果を再利用すれば、解答本体を編集した後のビルドでも効果がある。ただし、単に`bits/stdc++.h.gch`を置く案には現在のinclude順による問題がある。先に`atcoder/all`からC++トークンを読み込むため、後続の`bits/stdc++.h`でPCHを利用できない。[GCCのPCH仕様](https://gcc.gnu.org/onlinedocs/gcc-15.2.0/gcc/Precompiled-Headers.html)

さらに、配布設定の`-fmodules`と従来のPCHは併用できない。GCC 15.2の判定処理はモジュール有効時のPCH利用を拒否し、`-fmodules`付きの`-x c++-header`はヘッダーユニットの生成を意味する。PCHとして試すには、生成と使用の両方で`-fno-modules`を指定する必要がある。[GCC 15.2の実装](https://github.com/gcc-mirror/gcc/blob/releases/gcc-15.2.0/gcc/c-family/c-pch.cc#L209)、[GCC 15.2のモジュール仕様](https://gcc.gnu.org/onlinedocs/gcc-15.2.0/gcc/C_002b_002b-Modules.html)

これは`-O2`やライブラリ対応を削る変更ではないが、公式と同じ全フラグを維持する案でもない。対象を現在の雛形と同じ通常の`#include`形式の解答に限定して検証する。`import`を使う解答にはモジュールを有効にした別の経路が必要となる。また、`-fno-modules`では`__cpp_modules`の定義も変わるため、`#include`だけでも条件分岐によって挙動が変わり得る。採用する場合も正式設定での再確認を条件にする。[GCC 15.2の機能マクロ定義](https://github.com/gcc-mirror/gcc/blob/releases/gcc-15.2.0/gcc/c-family/c-cppbuiltin.cc#L1106)

モジュールを維持してヘッダーユニットを構築する案もあるが、キャッシュの配置や互換性の検証が増えるため、今回の補助PCH測定から効果を断定しない。

採用するなら、両方をまとめた共通ヘッダーを最初に読む構成か、include順の変更を検証する。提出する解答がローカル専用ヘッダーへ依存しない形を選ぶ。

PCHはコンパイラのバイナリ、言語、マクロ、最適化・デバッグ設定、CPU関連設定との互換性が必要。通常用とデバッグ用を分け、`-march=native`によるCPU差やコンパイラ更新時の再生成も扱う。初回生成時間・ファイルサイズ・無効化・並行実行の費用を含めて比較する。GCCは互換性のないPCHを無視するため、`-H`などで実際に使用されたことも確認する。[GCCのPCH仕様](https://gcc.gnu.org/onlinedocs/gcc-15.2.0/gcc/Precompiled-Headers.html)

任意の解答へ無条件に`-include`を追加する設計には注意が必要。解答がヘッダーより前で定義したマクロの意味が変わる場合がある。標準雛形向けの利用と、独自の解答への適用条件を明確にする。

### 4. 再テスト時だけビルドを省く

解答を編集していない場合は、既存実行ファイルで`oj test`だけを行う専用タスクが最小の方法。編集直後のビルド時間は短くならず、最後にビルドした解答との一致確認が必要になる。

自動省略するなら、解答本体だけの更新時刻では不十分。ローカルヘッダー、コンパイラ、フラグ、出力先も追跡する。また、現在はデバッグビルドも同じ`a.out`へ出力するため、通常ビルドとデバッグビルドを混同しないことが必要。失敗したビルドの古い実行ファイルも再利用しない。

### 5. ccacheは補助候補

現在の一段のコンパイル・リンクに`ccache`を前置するだけではキャッシュされない。`-c`でオブジェクトを生成する処理とリンクを分ける必要がある。完全に同じ解答の再ビルドには効くが、解答を編集する通常の競プロ作業では毎回のキャッシュヒットを期待できない。リンク時間も残る。[ccache公式文書](https://ccache.dev/manual/latest.html)

PCHとの併用には追加の条件があり、マクロ変更の検出を緩める設定も伴う。まず別々に評価し、導入目的が確定してから検討する。[ccacheのPCH対応](https://ccache.dev/manual/latest.html#_precompiled_headers)

### 優先を下げる案

| 案 | 優先を下げる理由 |
| --- | --- |
| 通常ビルドを`-O0`へ変更 | コンパイル短縮と実行速度が交換条件になる。2秒制限で本番相当のビルドなら通る解答がタイムアウトする可能性がある。まず`-O2`維持の案を試す。[GCCの最適化設定](https://gcc.gnu.org/onlinedocs/gcc-15.2.0/gcc/Optimize-Options.html) |
| リンクフラグを一律に削除 | 標準ライブラリ・ACLだけの解答と、GMPやOR-Tools等を使う解答の必要条件が異なる。全ライブラリ対応を維持するなら一律削除は避ける |
| ソースのinclude名から必要ライブラリを自動推定 | 推移的な依存、条件付きinclude、ローカルヘッダーを正しく扱う費用が大きい |
| `-j`やCPU数の増加を最初に試す | 解答は通常1つの翻訳単位。ビルド処理の並列化より、どの工程が遅いかの計測が先 |
| Dockerの構築並列数やイメージキャッシュの変更 | コンテナ構築への設定であり、このタスクによる解答のビルドは別の処理 |

WSLでリポジトリを`/mnt/c`等に置いている場合は、WSL側のファイルシステムとの比較も行う。READMEは既に`~/projects`への配置を案内している。利用者の配置が異なる場合の候補であり、今回その条件は未確認。[Microsoftのファイル配置ガイド](https://learn.microsoft.com/en-us/windows/wsl/filesystems)

## 反映範囲と採用時の検証

| 変更先 | 利用環境への反映 |
| --- | --- |
| `.vscode/tasks.json`へ試験用のリンカー指定を追加 | ワークスペース側の設定。既存イメージに`lld`があればコンテナ再構築をせず試せる |
| `config/atcoder-cli/cpp/main.cpp`のincludeを変更 | 次回取得する問題へ反映。既存解答は独立したコピー |
| イメージ内の`atcoder-g++`やPCH生成処理を変更 | 修正版イメージの発行・検証と固定ダイジェストの更新が必要 |

`atcoder-g++`は通常ビルド、デバッグ、環境検証で共用している。共通設定を変える場合は、その全経路を検証する。タスクだけに`lld`を指定した場合、ラッパーを直接呼ぶ現在のコンテナ検証にはその指定が届かないため、候補設定での実行確認を加える。タスク引数に関する構成テストの期待値も更新する。

修正版イメージを採用するときは`.devcontainer/devcontainer.json`と`.devcontainer/Dockerfile.prebuilt`を同じ検証済みダイジェストへ揃える。`stable`タグの更新だけでは、現在の固定ダイジェストを使う利用者に反映されない。`prepare.py`はGCC構築より前のDockerレイヤーにあるため、設定を変えるだけでも重い構築工程を無効化し得る。`lld`を比較する目的で変更する必要はない。

採用の判断には、編集後のビルド・変更なしの再実行・デバッグから通常ビルドへの切り替えを含める。短い標準ライブラリ中心の解答、ACLを使う解答、重い外部ライブラリを使う解答で確認する。ソースファイル名やパスに空白がある場合、コンパイル失敗時にテストへ進まない場合も既存の保証を維持する。

## 採用方針

2026-10-05、利用者は`-O2`と全ライブラリ対応を維持してLLDを先に比較し、PCHは互換性を確認する方針を承認した。まず、解答を編集した後にも作用するLLDをタスクに適用した。変更なしの場合だけのビルド省略や、新しいコンパイルキャッシュは導入していない。

設定は戻しやすい変更なのでADRは作成していない。PCHを採用する場合は、対象となる解答・初回生成費・無効化条件を別途確定する。
