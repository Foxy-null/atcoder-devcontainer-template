# C++雛形の共有リンク不具合：調査と修正計画

調査日: 2026-09-19。以下の原因分析・計画に基づき、ディレクトリリンクへの変更、既存解答リンクの移行コマンド、実際のaccによる回帰テストを実装した。ローカルLinuxで新規回帰テストと既存の移植性チェックが成功。配布イメージの検証結果はPRに記録する。

## 結論

修正前の構成では、AtCoderの各問題の `main.cpp` がC++雛形へのシンボリックリンクとして作成される。リンクをたどって解答を書き込むと、雛形・別問題・別コンテストで同じ内容が見える。不具合報告と整合する動作をLinux上で再現した。

報告者の生成済みファイル、エディターの保存方法、使用イメージそのものは未確認。すべての保存方法で必ず共有先が更新されるという主張ではない。通常ファイルに置き換えて保存する方法ではリンクが切れる場合がある。

## 調査時点の仕様と実装（修正前）

| 段階 | 現在の処理 |
| --- | --- |
| 利用者が編集する雛形 | `config/atcoder-cli/cpp/main.cpp`。READMEは次回取得からの反映を案内 |
| イメージ作成 | `config.json`、`cpp/template.json`、`cpp/main.cpp` を `/usr/local/share/atcoder-cli` に格納 |
| 初期化 | `setup-atcoder-user` がイメージ内の `config.json` と `template.json` をハッシュに基づいて設定領域に配置 |
| 雛形の接続 | `$(acc config-dir)/cpp/main.cpp` をリポジトリの雛形へのリンクにする |
| 検証 | `verify-atcoder-toolchain` は上記のファイルリンクを必須としている |
| AtCoder取得 | VS Codeタスク → `atcoder-workflow download` → `acc new CONTEST --force` |
| 問題ファイル作成 | `template.json` の `task.program: ["main.cpp"]` に基づくコピー |
| 提出 | `task.submit: "main.cpp"` |
| yukicoder取得 | タスク内の通常の `cp` による内容コピー。新規ファイルでは同じリンク複製経路を通らない |

`template.json` は現状ではイメージ内の版が初期化の正本であり、リポジトリの同ファイルを編集しても直ちには反映されない。一方、雛形の `main.cpp` はリンク経由で直ちに参照される。

## 原因の根拠

Dockerfileは `atcoder-cli 2.2.0` を指定している。
[npmメタデータ](https://registry.npmjs.org/atcoder-cli/2.2.0)が示すソースコミットは `3be1031154a923de74769be1c993e1bf75cad70e`、依存する `fs-extra` は `^8.1.0`。

[atcoder-cliのinstallTaskTemplate](https://github.com/Tatamo/atcoder-cli/blob/3be1031154a923de74769be1c993e1bf75cad70e/src/template.ts)は次のオプションでコピーする。

```ts
await fs.copy(source, dest, {overwrite: false, errorOnExist: true});
```

リンク先を実体化する `dereference` は指定されていない。
[fs-extra 8.1.0のcopy](https://github.com/jprichardson/node-fs-extra/blob/8.1.0/lib/copy/copy.js)はこの場合 `lstat` でコピー元を調べ、リンクなら `readlink` と `symlink` でリンクを複製する。

```text
acc設定/cpp/main.cpp ──────────→ リポジトリのC++雛形
abc475/a/main.cpp ─────────────→ 同じC++雛形
abc475/b/main.cpp ─────────────→ 同じC++雛形
abc476/a/main.cpp ─────────────→ 同じC++雛形
```

`--force` を外すだけでは新規生成時のリンク複製を防げない。通常ファイルの解答は `program` の上書き禁止で保護されるが、これはリンクの独立性を保証しない。`static` は上書き対象なので代替にしない。

## 実施した検証と限界

WSLのLinux一時領域にNode.js 22.14.0と `fs-extra@8.1.0` を用意し、実際のライブラリに上記と同じ引数を渡した。既存の利用者ファイルは使用していない。

- 現行構成で3つの解答がリンクになることを確認。
- Aの書き換えが雛形、B、別コンテストの解答に波及することを確認。
- 修正候補のディレクトリリンク経由では各解答が通常ファイルになることを確認。
- 修正候補でAを編集してもBと雛形が変わらないことを確認。
- 雛形を更新すると新規作成分のみが新しい内容となることを確認。
- 既存解答への再コピーは拒否され、その内容が保持されることを確認。

これはコピー層の再現試験であり、`acc new`、AtCoderへの通信、配布済みコンテナでの完全な結合試験ではない。修正実装時には実際のacc経由で検証する。

既存の `check-portability.py` はyukicoderの通常コピーをモック環境で確認しているが、AtCoderの雛形展開は検証しない。`check-container.sh` も問題ファイルの生成・独立性を検証していない。

## 推奨する修正計画

### 1. 雛形を通常ファイルとしてaccに見せる

`main.cpp` 単体のリンクを廃止し、`$(acc config-dir)/cpp` をリポジトリの `config/atcoder-cli/cpp` ディレクトリへのリンクにする。末尾の `main.cpp` は通常ファイルなので、accの既存コピー処理で独立した解答になる。雛形の変更も次回取得に反映され、直接の `acc new` / `acc add` も同じ仕組みで動く。

- `setup-atcoder-user`: 既存の管理対象cppディレクトリを安全に移行し、ディレクトリリンクを作る。カスタマイズ済みの未知の内容は削除せず、元ディレクトリを退避するか移行を止めて明示する。
- `template.json` もリポジトリ側を正本とする。リンク経由でイメージ版をinstallしたり、リポジトリのMakefileを削除したりしないよう、既存の配置・ハッシュ管理を整理する。
- `verify-atcoder-toolchain`: ディレクトリリンク先と、末尾の雛形が通常ファイルであることを検証する。現在のファイルリンク必須条件を置き換える。
- READMEとoptions文書: 雛形と解答の区別、template.jsonの反映方法を説明する。

単に起動時に雛形を通常コピーする案では、起動後の雛形変更が次回取得に反映されない。取得ラッパーで毎回同期する案では直接のacc操作が抜ける。上流への `dereference: true` 提案は可能だが、本リポジトリの修正をその採用・リリース待ちにしない。

### 2. 生成済みの解答リンクを救済する

新規生成だけ直しても既存のリンクは残る。移行処理はまず対象一覧を出せるものとし、管理対象の問題ディレクトリ内で既知の雛形を指す `main.cpp` だけを扱う。

- 雛形を変更・復元する前に、現在の内容とリンク先情報をバックアップする。
- 各リンクの現在の内容を同じディレクトリの一時通常ファイルへ書き、リンク自体を置換する。リンク経由で上書きしてはいけない。
- 通常の解答ファイルと無関係なリンクは変更しない。切れたリンク・未知のリンク先は一覧化して個別対応する。
- 再実行しても既存解答を変えない。
- 過去に共有先へ上書きされた各問題の独自内容は、リンクを切るだけでは復元できない。Git、エディター履歴、提出履歴等からの復旧を別途案内する。

### 3. 回帰テストを追加する

Linux上で実際のaccを使い、テスト用の設定・雛形・問題ディレクトリを隔離する。AtCoderへの通信に依存しない固定の問題情報を利用し、実際の雛形展開を通す。

1. 2コンテスト・複数問題を生成し、解答が通常ファイルである。
2. Aを編集してもB・別コンテスト・雛形が変わらない。
3. 雛形編集後の新規問題だけに変更が反映される。
4. 再取得・追加取得でも既存の通常解答を保持する。
5. 旧設定からの移行、未知のカスタマイズの保持、初期化の再実行を検証する。
6. 既存解答リンクの移行後に内容を保持し、通常ファイル・無関係なリンクを変更しない。
7. yukicoder側の新規作成と既存解答保持も確認する。

既存のコンテナ検証に組み込み、可能ならPR時の軽量Linux検証でもコピー・移行試験を実行する。重いコンパイラ再構築だけを回帰検知の入口にしない。

### 4. 配布イメージまで反映する

スクリプトはイメージへCOPYされており、ソース編集だけでは現在の固定イメージは更新されない。

修正版イメージを既存CIで生成・検証し、`.devcontainer/devcontainer.json` と `.devcontainer/Dockerfile.prebuilt` の固定ダイジェストを同時に更新する。そのうえで利用者向けに更新・コンテナ再構築・既存解答の移行手順を案内する。stableタグの更新だけでは固定ダイジェストの利用者に届かない。

## 完了条件

新規解答が独立し、雛形更新は次回取得分だけに反映され、既存解答を失わず移行できること。実際のaccを使う回帰テストと既存の必要チェックが通り、修正版イメージを参照する配布設定・利用者向け移行手順まで揃っていること。
